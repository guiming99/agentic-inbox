# v1.0.5 Retention / Cleanup Design

## Status

Design only. This document does **not** enable automatic cleanup.

## Current lifecycle findings

- Email metadata and attachment metadata live in the Mailbox Durable Object SQLite database.
- Attachment bytes are stored in the primary `BUCKET` R2 bucket under:
  `attachments/{emailId}/{attachmentId}/{safeFilename}`.
- `MailboxDO.deleteEmail()` deletes the email row and returns attachment metadata.
- The API delete route then deletes the corresponding R2 objects.
- SQLite foreign-key cascade removes attachment rows when an email row is deleted.
- The existing delete path therefore already has an explicit R2 cleanup step; v1.0.5 should not replace it casually.
- The Worker currently has no scheduled/cron trigger.

## Safe retention policy

Automatic retention must be **opt-in**. Existing mail must never start disappearing merely because v1.0.5 is deployed.

Recommended initial scope:

1. Only `trash` and `spam` are eligible.
2. `draft`, `inbox`, `sent`, and `archive` are never automatically purged by the first implementation.
3. Retention is disabled unless mailbox settings explicitly enable it.
4. Retention days must be a bounded positive integer; invalid values disable cleanup.
5. Cleanup is bounded per mailbox/run to avoid Durable Object and R2 subrequest spikes.
6. Cleanup must use the indexed `(folder_id, date)` path rather than a full-table scan.

## R2 consistency rule

A cleanup implementation must preserve the current relationship:

`email row -> attachment rows -> R2 objects`

The Durable Object cannot atomically transact with R2. Therefore the cleanup path must be designed so a partial R2 failure does not make the email disappear silently without an observable error. The first implementation should reuse the existing attachment-key convention and log failures with mailbox/email identifiers.

## Scheduling

A future implementation may add a Cloudflare scheduled trigger, but it must:

- enumerate mailboxes safely;
- read each mailbox's opt-in retention setting;
- invoke a bounded Durable Object cleanup operation;
- keep email receiving/sending independent of cleanup;
- use `waitUntil`/scheduled execution only for cleanup work;
- continue processing other mailboxes if one mailbox fails;
- avoid changing the email receive handler.

## Explicit non-goals

- No cleanup of Inbox/Sent/Archive in the first version.
- No deletion based only on database age without folder eligibility.
- No bulk unbounded `DELETE` statement.
- No replacement of the existing manual delete route.
- No CloudMail code import; CloudMail is only the architectural reference.
